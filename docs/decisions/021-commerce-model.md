# ADR 021: One commerce model for every lab

**Status:** Accepted

## Decision

ZeroShift's commerce domain is seven entities, each owned by exactly one service and stored in that
service's own database (Flyway is the schema's source of truth; jOOQ classes are generated from it).

| Entity | Owner (database) | Table(s) |
|---|---|---|
| Customer | order-service (`orders`) | `customer` |
| Voucher | order-service (`orders`) | `voucher` |
| Order, OrderItem | order-service (`orders`) | `orders`, `order_item` (+ `event_store`, the source of truth) |
| Invoice | order-service (`orders`) | `invoice` |
| Product (catalog and stock) | inventory-service (`inventory`) | `product`, `reservation`, `reservation_item` |
| Payment | payment-service (`payments`) | `payment` |
| Shipment | shipping-service (`shipping`) | `shipment` (unchanged) |

The read model (order-query-service) and the race condition lab use the same names, types and
money rules. The migration lab keeps its legacy SQL Server `customers`/`orders` on purpose: that
legacy shape is what it migrates.

### Conventions

- **Ids** are `UUID` (generated by the application; `DEFAULT gen_random_uuid()` for seeds).
- **Money** is `NUMERIC(12,2)` in SQL and `BigDecimal` at scale 2 in Java, rounded `HALF_EVEN`
  (`io.zeroshift.contracts.Money`). **Currency** is `CHAR(3)` matching `^[A-Z]{3}$`; the lab sells in one
  currency, `commerce.currency` (default `USD`), and every amount carries it.
- **Enums** are `TEXT` with a `CHECK` listing the values (the Java enum's names).
- **Timestamps** are `TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()`: `created_at`, `updated_at`,
  and one per lifecycle step (`paid_at`, `authorized_at`…), null until it happens.
- **Optimistic versions** are `BIGINT NOT NULL DEFAULT 1`, incremented by every update.
- **Foreign keys** exist inside a database only. Across services a reference is a plain `UUID` (no
  FK, no join): each service owns its data and learns about others through messages.

### Snapshots: history never changes

An order copies everything it depends on when it is placed: each item's product id, SKU, name and
unit price; the voucher's code, type and value; the tax rate. Later catalog price or name changes,
voucher edits or deactivation never alter a placed order, its items, its invoice or its events.

### Money, deterministically

`order-service`'s `Pricing` computes, all at scale 2 and `HALF_EVEN`:

```
item.subtotal   = unit_price × quantity
order.subtotal  = Σ item.subtotal
order.discount  = 0 without a voucher; otherwise
                  FIXED:      min(value, subtotal)
                  PERCENTAGE: round(subtotal × value / 100)
                  then capped by maximum_discount (if set)
item.discount   = order.discount split across items in proportion to item.subtotal
                  (largest remainder in cents; ties go to the earlier line), so Σ item.discount = order.discount
item.total      = item.subtotal − item.discount
order.tax       = round((order.subtotal − order.discount) × order.tax_rate)
order.total     = order.subtotal − order.discount + order.tax
```

`CHECK` constraints enforce `total = subtotal − discount + tax`, `0 ≤ discount ≤ subtotal` on orders and
invoices, and `subtotal = unit_price × quantity`, `total = subtotal − discount` on items. The tax rate is
`commerce.tax-rate` (default `0.0800`), snapshotted on the order.

### Tables

**orders database (order-service)**

```sql
customer(id UUID PK, name TEXT NN, email TEXT NN, phone TEXT, created_at, updated_at)
  UNIQUE INDEX customer_email ON customer (lower(email))
voucher(id UUID PK, code TEXT NN UNIQUE CHECK (code = upper(code)),
  discount_type TEXT NN CHECK IN ('FIXED','PERCENTAGE'), value NUMERIC(12,2) NN CHECK (value > 0),
  minimum_amount NUMERIC(12,2) NN DEFAULT 0, maximum_discount NUMERIC(12,2),
  usage_limit INT CHECK (> 0), usage_count INT NN DEFAULT 0 CHECK (usage_count >= 0 AND (usage_limit IS NULL OR usage_count <= usage_limit)),
  valid_from TIMESTAMPTZ NN, valid_until TIMESTAMPTZ, active BOOLEAN NN DEFAULT true,
  version, created_at, updated_at;  CHECK percentage value <= 100; CHECK valid_until > valid_from)
orders(id UUID PK, customer_id UUID NN FK customer, status TEXT NN CHECK IN ('PLACED','PAID','RESERVED','SHIPPED','CANCELLED'),
  currency CHAR(3) NN, subtotal, discount, tax_rate NUMERIC(5,4) NN, tax, total NUMERIC(12,2) NN,
  voucher_id UUID FK voucher, voucher_code TEXT, voucher_discount_type TEXT, voucher_value NUMERIC(12,2),
  payment_id UUID, reservation_id UUID, tracking_number TEXT, cancel_reason TEXT,
  version BIGINT NN (= the event stream's version), placed_at, updated_at, paid_at, shipped_at, cancelled_at)
  INDEX (customer_id, placed_at DESC), (placed_at DESC), (status)
order_item(id UUID PK, order_id UUID NN FK orders ON DELETE CASCADE, line_no INT NN, product_id UUID,
  sku TEXT NN, product_name TEXT NN, unit_price, quantity INT NN CHECK (1..999), subtotal, discount, total;
  UNIQUE (order_id, line_no))
invoice(id UUID PK, order_id UUID NN UNIQUE FK orders, number TEXT NN UNIQUE, status TEXT NN CHECK IN ('ISSUED','PAID','VOIDED'),
  currency, subtotal, discount, tax, total, issued_at NN, paid_at, voided_at, created_at, updated_at)
  number = 'INV-' || year || '-' || lpad(nextval('invoice_number_seq'), 6, '0')
idempotency_key(key TEXT PK, request_hash TEXT NN, order_id UUID NN FK orders, correlation_id UUID NN, event_id UUID NN, created_at)
```

Kept as they are: `event_store`, `order_snapshot`, `saga`, `saga_transition`, `lease`, and the platform
tables. Deleted: `product` (the catalog now lives in inventory).

**inventory database (inventory-service)**

```sql
product(id UUID PK, sku TEXT NN UNIQUE CHECK (sku ~ '^[A-Z0-9][A-Z0-9-]{2,39}$'), name TEXT NN, description TEXT NN DEFAULT '',
  price NUMERIC(12,2) NN CHECK (>= 0), stock INT NN CHECK (>= 0), version, active BOOLEAN NN DEFAULT true, created_at, updated_at)
reservation(id UUID PK, order_id UUID NN UNIQUE, status TEXT NN CHECK IN ('RESERVED','REJECTED','RELEASED'), reason TEXT, created_at, updated_at, released_at)
reservation_item(reservation_id UUID FK reservation ON DELETE CASCADE, product_id UUID FK product, quantity INT NN CHECK (> 0), PK (reservation_id, product_id))
```

`stock` is what can still be sold. Reserving takes it with one conditional update per product, in
product-id order (so two reservations never deadlock):
`UPDATE product SET stock = stock - :q, version = version + 1 WHERE id = :id AND active AND stock >= :q`.
If any item fails, the transaction rolls back and a `REJECTED` reservation (no items) is recorded.
Releasing gives the quantities back. This is exactly the race condition lab's atomic update.

**payments database (payment-service)**

```sql
payment(id UUID PK, order_id UUID NN, idempotency_key TEXT NN UNIQUE,
  status TEXT NN CHECK IN ('PENDING','AUTHORIZED','DECLINED','REFUNDED','VOIDED'),
  method TEXT NN DEFAULT 'CARD' CHECK IN ('CARD'), amount NUMERIC(12,2) CHECK (> 0), currency CHAR(3),
  -- amount and currency are both set, or both null (a VOIDED row: refunded before anything was charged)
  provider TEXT NN, provider_reference TEXT, failure_reason TEXT,
  created_at, updated_at, authorized_at, declined_at, refunded_at, voided_at)
  INDEX (order_id)
```

The idempotency key (from `AuthorizePayment.idempotencyKey`; for the saga, `order:<orderId>:authorize`)
is claimed with `INSERT … ON CONFLICT (idempotency_key) DO NOTHING` before the gateway is called, and
sent to the gateway as its `Idempotency-Key`. A redelivered command finds the key and answers with the
same outcome; a request that reached the gateway but crashed before recording (still `PENDING`) retries
the gateway with the same key. `gateway_call` stays (it belongs to the resilience labs).

### Messages

Everything is additive, so no schema version changes (the registry's rule: adding a field is
backward compatible):

- `OrderLine` gains `productId`, `name`, `subtotal`, `discount` and `total`. It keeps `sku`,
  `quantity` and `unitPrice`.
- `OrderPlaced` (still **v2**) gains `customerName`, `subtotal`, `discount`, `taxRate`, `tax`,
  `voucherCode` and `invoiceNumber`.
  - A payload written before these fields existed decodes with neutral values: `subtotal = total`,
    no discount or tax, the customer id as the name. Each line gets `subtotal = total =
    unitPrice × quantity` and `name = sku`. That is exactly what those orders were.
  - The history lab's v1 writer also drops these fields, because a v1 writer never had them.
- `AuthorizePayment` gains `idempotencyKey`.
- `PaymentAuthorized` and `PaymentRefunded` gain `currency`. `PaymentRefunded` has a null currency
  and `0.00` when nothing was ever charged.
- `ReserveStock.StockLine` gains `productId`.
- The saga is unchanged: payment, then stock, then shipment. The invoice is issued with the order,
  marked paid on `PaymentAuthorized`, and voided on cancellation, which also returns the voucher's use.

### APIs

- `POST /orders` (order-service): `{customerId: UUID, items: [{sku, quantity}], voucherCode?}`. It
  checks the customer, prices each item from the inventory catalog (`GET /products?sku=…`, a
  synchronous call: if the catalog is down, placing an order fails with `503 CATALOG_UNAVAILABLE`),
  applies and redeems the voucher, and issues the invoice, all in the order's transaction. The answer
  is `OrderAccepted` with the amounts and the invoice number.
- `GET /customers`, `GET /customers/{id}`, `GET /vouchers` (order-service); `GET /products`,
  `GET /products/{id}` (inventory-service); the read model's `GET /orders` gains amounts, voucher,
  invoice and customer name.
- New error codes: `UNKNOWN_CUSTOMER` (422), `VOUCHER_NOT_APPLICABLE` (422), `VOUCHER_EXHAUSTED` (409),
  `CATALOG_UNAVAILABLE` (503).

### Demo data

Each service seeds its own data when its tables are empty (`commerce.demo-data`, on in Compose, off in
tests), with realistic randomized values: order-service seeds customers and vouchers, and
inventory-service seeds the product catalog. Orders, payments and invoices are never inserted
directly. `scripts/seed_commerce.py` places randomized orders through `POST /orders`, so every payment,
reservation, invoice and projection comes from the real saga.

## Why

- Before, the same products lived in two unlinked tables, customers were free-text names, money had
  four types, and there were no vouchers, tax or invoices. The labs had to invent their own orders.
- One owner per entity keeps the lessons clean. The catalog-and-stock owner is where the race for the
  last item happens. The order owner snapshots what it sold. The payment owner deduplicates charges
  by key.
- Keeping the event store as the source of truth, and updating the `orders` tables in the same
  transaction, keeps the event sourcing, history and saga labs intact, while giving invoices, vouchers
  and customers real foreign keys. The table is a cache of the fold, and the lab can compare the two.

## Consequences

- Placing an order now depends on inventory-service being up: a synchronous dependency, visible in
  traces, and a failure mode worth showing.
- Events written before the commerce model still decode: missing fields take neutral values (no
  discount, no tax).
- The commerce databases are recreated from the new migrations; the lab's local data is disposable.
